# yt-llm-director

Direct an edit with a model in three roles instead of the fixed rules. The screenwriter reads the brief and the shotlog and writes `shot_plan.json` (structure, beats, which shot goes where and roughly how long). The editor turns the plan into exact source timecodes. The reviewer checks the draft against the brief and the editing rules and sends fixes back for at most two rounds by default (max three). When the loop cannot finish, the rule-based `scripts/director.py` takes over. All commands run through `yt <tool>`.

## Step 1: direct an edit with the loop

```bash
yt llm_director --workspace /path/to/workspace \
  --brief "about 90 seconds, chronological, calm start, more energy towards the end, ambient sound only"
yt llm_director --workspace /path/to/workspace --brief-file brief.txt --json
yt llm_director --workspace /path/to/workspace --brief "..." --rounds 2 --out my_edit.json
```

- `--workspace` is required and must hold `shotlog.json`, `ingest.json`, `motion/<stem>.json` and `quality/<stem>.json` — exactly what `scripts/director.py` reads. Without `shotlog.json` it falls back to the rules immediately and says so in the warnings.
- Give exactly one of `--brief` (inline text) or `--brief-file` (path). Neither exits 2 with one `[error] ...` line on stderr.
- `--out` (default `WORKSPACE/edit.json`) is the edit list; `--plan-out` (default `WORKSPACE/shot_plan.json`) is the plan.
- `--speed-ramp` (default off) lets the middle half of long camera moves play up to 1.2x on screen; without it every slot plays at normal speed.
- `--rounds` (default 2, max 3) is the number of review rounds. `--model` overrides `models.director`; `--budget-usd` overrides `llm_budget_usd`; `--important-max-s` caps a hero or semantic-move slot (default: from the pacing table for the brief's target duration, 6.0 s ceiling).
- `--reasoning-effort` (`low`, `medium`, `high` or `off`) sets how much hidden reasoning the model spends; it overrides `director.reasoning_effort` in the config, which defaults to `medium`. Every call the loop makes — screenwriter, editor, reviewer and the `--interpret-feedback` reply — carries it as OpenRouter's `reasoning` body (`off` disables reasoning). There is no environment variable.
- `--beats FILE` (optional) is the beat grid JSON from `scripts/beats.py --out` (keys `beat_s`, `downbeat_s`, `beat_period_s`/`duration_s`, either under `measurement` or at the top level; times are absolute seconds in the music, which starts at timeline 0). With it every timeline cut snaps to a beat (the shift limit is the slot's allowed length range; a downbeat or half-bar cut may move up to half a bar, else a warning and the cut stays) and every cut prefers the nearest downbeat when it lies inside the slot's allowed length range, otherwise a half-bar beat, otherwise the nearest beat, so every cut is on a beat; every non-first slot joins with a hard cut. The rule-based fallback and the `--dry-run` baseline get the same grid.
- `--target-duration-s`, `--order` and `--pacing` override the hints parsed from the brief; without them the brief is parsed the same way `router.py` parses it.
- After the last round a draft with violations is repaired from the shot facts (bad cut rebuilt, slot outside the plan dropped, weaker shot of a same-take jump cut dropped, a missing top star swapped in for the weakest non-star slot of a compatible length) and kept; a missing hero photo is only a warning. A repair never drops a shot the owner named (add or drop) or a member of the owner's dropped group, and a shot the owner asked to drop — with every member of its star group — is never put back by a repair, the star rule or the reviewer. `edit.json meta.director` records `by` (`llm`/`rules`), `approved` and the notes (repairs, fallback reason), shown by explain.html.
- `--fallback-rules` (default) falls back to `scripts/director.py` when the loop fails or the repaired draft is still invalid; `--no-fallback-rules` makes the failure an error instead. The owner's `add_keys`/`drop_keys` (read from the last `reply` row whose `text` prefixes the feedback) reach the rule fallback as `--add-shots`/`--drop-shots`, so a fallback still applies the owner's explicit changes.
- `--feedback TEXT` (repeatable) revises the current edit from plain words against its short ids, e.g. `--feedback "drop 0071/s2, tunnel longer"`. Every flag is appended as one JSON line (`ts`, `action`, `text`, `tool`) to `WORKSPACE/feedback.jsonl` (the learning store, append-only, written even when the run later falls back), the up-to-date check is skipped for this run, and the screenwriter and editor user messages both gain a block before the plan/facts with the feedback texts, the previous edit's used slots (id, `shot_key`, clip, in/out or duration, reason) and its rejected candidates (id + reason from `edit.json` `decisions[]`), so every short id in the feedback resolves; with no previous `edit.json` the block says so and the feedback still reaches the screenwriter. The code validator is unchanged — the feedback never overrides the edit grammar. The `--json` summary gains `feedback` (the list given).
- `--interpret-feedback TEXT` (with `--version vNNN` to read a version's edit) makes one cheap `metadata`-role call that says how the director reads a feedback request, writes no edit, prints `reply`, `can_do`, `missing_tool`, `estimate_usd`, `estimate_s`, `wall_time_s` and `llm_cost_usd`, and appends one `action: "reply"` line to `WORKSPACE/feedback.jsonl` carrying `can_do` and `missing_tool`. `can_do` is `"all" | "part" | "none"`; the reply resolves a plain-word request against the shot summaries, subjects and clip numbers and names the shots it means, asking for a short id only when two readings are equally likely. Exit `2` on a usage or config error, `3` on a runtime failure.
- `--force` rewrites even when the output is up to date. `--json` prints the machine-readable summary. It never asks questions.
- The director reads the instance **notebook** before every edit (the file at `--notebook`, else `YT_PIPELINE_NOTEBOOK`, else `notebook.path` in the config) and hands its lessons to the screenwriter, the editor and the reviewer; with no notebook set it reads nothing. The notebook is edited with `yt-notebook`.

## Step 2: agent mode (prepare and apply)

A host coding agent can direct the edit without an OpenRouter key. `--prepare` writes `<workspace>/director/inputs.md` — the brief, the brief settings, the editing rules, the shortlisted shots and their shot facts, plus the two output shapes — and makes no model call. The agent writes `<workspace>/shot_plan.json` (schema `schemas/shot_plan.schema.json`) and `<workspace>/edit.json` (the editor answer shape `{"slots": [...], "notes": [...]}`), then `--apply` validates both against the schemas and the editing grammar, repairs mechanical faults with the same machinery the loop uses and writes the final `edit.json` with `meta.director.by = "agent"`.

```bash
yt llm_director --workspace /path/to/workspace --brief "..." --prepare --json
yt llm_director --workspace /path/to/workspace --brief "..." --apply --json
```

- Both require `--workspace` and exactly one of `--brief` / `--brief-file`. `--prepare` accepts `--out`, `--plan-out`, `--important-max-s`, `--target-duration-s`, `--order`, `--pacing`, `--beats`, `--music`, `--ambient-under-music-db`, `--speed-ramp` and `--json`; `--apply` accepts the same plus `--force`. `--prepare` does not accept `--force`.
- `--prepare` and `--apply` are mutually exclusive with each other, `--interpret-feedback` and `--dry-run`; more than one is a usage error naming the conflict.
- `--prepare` needs `shotlog.json` (no fallback) and writes no `edit.json`; when `--beats`/`--music`/`--ambient-under-music-db`/`--speed-ramp` are given it writes the beat grid and the music facts into `director/inputs.md` too. The `--json` summary is `{"status": "prepared", "inputs", "candidates", "warnings", "wall_time_s", "llm_cost_usd": 0.0}`.
- `--target-duration-s 0` ("All good shots") works in agent mode exactly as in the loop: the target becomes the `estimate_all_good` seconds (at least 20 s) and the long-cut pacing is used.
- `--apply` reads the plan and the answer, rejects an unrepairable edit with a usage error naming the first blocking rule, and writes the final edit; the `--json` summary is `{"status": "written", "out", "plan", "slots", "total_duration_s", "validator_violations", "warnings", "wall_time_s", "llm_cost_usd": 0.0}`. When `edit.json` is already a full edit (a `video` list) and `--force` is not given, it writes nothing and reports `status: "skipped"`; with `--force` it re-applies from the plan and the existing edit's slots.
- After `--apply` the host agent runs the same learning pass the web app runs: `yt notebook --notebook <file> --learn --workspace <workspace>` makes one cheap `metadata`-class model call and writes at most 3 short lessons from the feedback since the last pass (marker `<workspace>/.learn.json`). It never blocks the edit and a failure only logs.

## Step 3: dry run and the rule-based baseline

```bash
yt llm_director --workspace /path/to/workspace --brief "..." --dry-run --json
```

`--dry-run` runs **only** the screenwriter: it writes `shot_plan.json`, calls no editor and no reviewer, and writes no `edit.json`. It also runs `scripts/director.py` as a subprocess with a throwaway `--out` and reports the rule-based baseline — the slot count, the total duration and the top reasons — so the LLM edit can be compared against the deterministic one. The `--json` summary carries a `baseline` object with `slots`, `total_duration_s` and `reasons`.

## Step 4: read the result

`shot_plan.json` is validated against `schemas/shot_plan.schema.json` and `edit.json` against `schemas/edit.schema.json` before they are written, so a run either leaves complete, valid files or none.

`edit.json` `meta.director.review` carries the last reviewer verdict: `approved` plus `objections`, each with `slot` (the slot id), `shot` (its 1-based position in the edit) and `text` (the plain-word fix). Old edits without `review` stay valid and the rule-based fallback writes none.

The `--json` summary is a flat object: `status` (`written`/`skipped`/`fallback`), `out`, `plan`, `rounds_used`, `approved` (bool or null), `fallback` (null or `"rules"`), `slots` (video slots written), `candidates` (the full eligible count), `shortlist` (rows offered to the screenwriter), `total_duration_s`, `validator_violations` (count of the last validation), `warnings`, `wall_time_s`, `llm_cost_usd` (the sum of the run's calls), `beat_snap` (the `--beats` snap tally `{"beats", "snapped", "unsnapped", "downbeats", "half_bar"}`, or null without a grid) and `feedback` (the `--feedback` texts given, `[]` without). When the loop ends with rule violations each one is also listed in `warnings` as `violation <slot id>: <rule>: <message>`. `--dry-run` adds `baseline` and `dry_run`.

Exit codes follow the table: `0` success (an edit was written, including a fallback), `1` finished but a human must look at the result, `2` usage, input or config error (nothing ran), `3` runtime failure after work started (including the budget running out with no fallback written).

## How the loop works

- **Shot facts.** For every eligible shot the tool computes the same usable window the rule-based director computes: the hold segment bounds for a hold, the overlapping motion move's handle window for a move, and for a **phrase** (a move with the hold it lands on) the move's handle-in through the hold's end with `landing_at_s` set to the hold's start. When the shotlog carries **content beats** for a quality segment (`beat_of` set), the segment contributes one fact per beat — key `<clip counter>/<segment id><beat id>` (e.g. `0072/s7b1`) — each with the beat's own range intersected with the move window, so a long take offers its approach and its exit as separate cuttable shots. `keep_whole` is true for a hero or a complete semantic move — it is the shot's own flag and the plan cannot turn it off. **Photo shots** (`media_type: "photo"`, key `<counter>/p1`) become photo facts: `photo` (file name, joined to the ingest `photos[]` for the path), `capture_time`, `subject_position`, `tags`, `score`, `summary`, `hero` and `similar_to`, with no window, no landing and a fixed 3 s target; burst-suppressed photos (`eligible: false`) never enter the pool. Only the shots that come out of this step with a usable window are offered to the screenwriter — the same cuttable pool the editor can cut — and the summary reports their count as `candidates`. The screenwriter does not see the whole pool: it gets a **shortlist** — every star (`common.moves.is_star`) plus the top-K rows by score (ties by key), K = 2 × the plan's slot count clamped to 24 and 60, plus every clip's best eligible segment (unless it is a whip short-hold) — returned in the shotlog's chronological order, and the summary reports its size as `shortlist`. The editor gets the facts of the planned shots, with the shot's own `keep_whole` and the plan's `target_s`.
- **Screenwriter.** One call with the playbook (`prompts/playbook.md`) plus `prompts/screenwriter.md`; the answer is parsed (markdown fences tolerated) and completed into a full plan, then validated. A parse or schema failure is retried once; a plan that still will not validate is a loop failure.
- **Editor.** One call with the playbook (`prompts/playbook.md`) plus `prompts/editor.md`; the answer becomes one video slot per plan slot, in plan order, with `clip`, `in_s`, `out_s` from the answer, `score`/`reason`/`role`/`motion_label`/`description` from the shotlog row (`reason` = the shotlog reason plus the plan's `why`), `cut` on the first slot and `crossfade` 0.3 on the others unless the editor said `cut`, `speed` 1.0, and the same `audio`/`captions`/`graphics` shape `scripts/director.py` writes. A **photo slot** answers with `duration_s` (2–4 s, default 3.0) instead of `in_s`/`out_s`; when the model gives `in_s`/`out_s` anyway the tool uses `out_s - in_s`. The tool emits `{"id", "kind": "photo", "photo", "duration_s", "ken_burns": ken_burns_for(subject_position, tags), "score", "reason", "transition", "description", "capture_time"}` and adds a `media_type: "photo"` row to `sources[]` per used photo. When the model's window breaks one of the two length rules the editor prompt states, the tool applies the spec's formula itself instead of looping to a fallback and records a `fixed <slot>` warning: a hero or semantic shot gets `window_out_s` with `window_in_s` at most `window_out_s - important_max_s` (the tail), and ordinary slot is trimmed to its target inside the pacing table's `slot_min`–`slot_max` for the brief's target duration (about 20 s → 1.5–2.5 s, about 90 s → 2–5 s, 3 min → up to 6 s; the absolute safety bounds are 1–12 s). A parse or schema failure is retried once. A plan slot the editor left without a usable answer is skipped and reported to the reviewer as `missing`; if it is still missing in the last draft the tool synthesises it from the shot fact (the spec's window, `fixed <slot>` warning) so a plan slot is never dropped. An answer with no usable slot at all is retried and, if it stays empty, is a loop failure.
- **Validator (code, not the model).** The draft is checked against the editing rules and every violation (slot id, rule, message) is handed to the reviewer. The rules: every plan slot has a cut window (`missing` when the editor produced none); every slot stays inside its shot's usable window (which ends where the steady motion ends — never on aimless movement after it); a landing phrase ends inside its hold at or after `landing_at_s` and its landing hold is never planned again; a cut trimmed from a longer window is centred on `peak_s` within 0.3 s (rule `peak`, unless the landing floor prevents it); the move policy is the only length authority, so the validator no longer forces a `keep_whole` window; ordinary slots stay inside the pacing table's `slot_min`–`slot_max` for the brief's target duration (1–12 s absolute); two slots from the same take are never back to back unless their windows touch within 0.5 s; two visually similar shots are never adjacent (the check compares the frames inside each slot's `in_s..out_s`, the windows actually in the edit, with the same embedding `similarity.py` uses, cached per window key; it falls back to the whole-segment `similar_to` check when a clip cannot be read; whole-segment similarity stays for the menu); two neighbouring slots that are beats of the same segment, or a `similar_to` pair, are a pointless jump cut — the validator raises `same_segment`/`similar` and the repair drops the weaker one, unless the owner's feedback asked for both (the plan marks the later slot `deliberate`); a key the owner asked to add, and a required star, are protected, so a pair with one protected key drops the other one; the director never marks it `deliberate` by itself. **Top stars** (heroes or scores >= `STAR_MIN_SCORE` 0.85, imported from `common/moves.py`) from the top `STAR_SHARE` (40 %) of the slots must be in the plan — one left out is a blocking `hero_missing` violation, repaired by swapping it in for the weakest non-star slot of a compatible length (within a factor of two, never creating a same-take jump cut), never by falling back to the rules. The required stars count once per group: two stars are one group when they are beats of one segment (same clip and `segment_id`) or a `similar_to` pair (groups are transitive), and only the best of each group is required; a group that contains any of the owner's drop keys is not required at all. **Photo slots** are 2–4 s (`photo_length`), have no window, landing or same-take rule, and a planned hero photo that is dropped is a `missing` violation (the tool synthesises it back); a dropped hero photo is still only the non-blocking `hero` warning. For a chronological brief the repair never breaks the order: after the repairs the edit and its plan are re-sorted by capture/source time before the beat snap, and a final check sorts any chronological edit that comes out of order. The reviewer's payload drops `description` and `reason` from each slot.
- **Move length policy (`common/moves.py`, D2-11; ramp optional and peak-centred since D2-12).** After the loop approves (or keeps its clean draft) and before the beat snap, the same shared policy runs on the record's slots (the shot facts supply window, landing floor, `peak_s`/`peak_source` and `keep_whole`; a `keep_whole` hero that is a static hold counts as a static shot), so the validator accepts a move longer than `slot_max` (up to the hero cap) on at most 15% of the slots. Normal speed is the default: `middle_speed` is 1.0 unless `--speed-ramp` is given (then the middle half of a move may play up to 1.2x); the editor never writes `middle_speed`. A cut shorter than its window is centred on the peak (`common/peak.py`: vision `peak_s`, else the OpenCV motion maximum, else the window middle) and clamped inside the window; a landing floor wins over the peak. Every other slot, every static or hold slot and every photo is clamped to `slot_max`. The beat snap absorbs its shifts in on-screen time and never lengthens a slot past its cap. `meta.speed_ramp` is stored; a different `--speed-ramp` value re-runs the edit.
- **Reviewer.** One call with the playbook (`prompts/playbook.md`) plus `prompts/reviewer.md`; it sees the repaired copy of the draft — the windows that ship, each slot carrying `keep_whole` and `max_screen_s` — and `approved: true` with no violations on that copy ends the loop. Its fixes cover only the brief, the story, the owner's request and lengths; a request for a different shot (a shot the editor cannot add or swap) goes to `notes`. Otherwise the fixes go back to the editor for another round. If the reviewer never approves, the last draft is kept only when it has zero violations (with a warning); otherwise the loop fails.
- **Beat snap (`--beats`).** After the edit is built, the timeline is the plain sum of the slot lengths (a beat grid makes every join a hard cut). Each cut — the end of each slot, final cut included — snaps to a beat within the slot's allowed length range (a downbeat or half-bar cut may move up to half a bar) by extending or trimming the previous slot: a video slot's `out_s` within `[in_s + 0.5, window_out_s]` (never below the phrase floor `landing_at_s + 0.75`; a hero or complete semantic move is left whole) and a photo's `duration_s` within `[2.0, 4.0]`, preferring a beat count that fits. **Every** cut prefers the nearest **downbeat** when it lies inside the slot's allowed length range, otherwise a **half-bar** beat (the downbeats plus two beat periods, so the bar count stays even), otherwise the nearest beat, so every cut is on a beat; when the downbeat nearest the cut is over the slot cap, the cut falls back to the nearest beat under the cap, so it still lands on a beat. The slot records which grid its cut used in `beat_grid` (`"downbeat"`, `"half_bar"`, `"beat"`, or `null` when it was not snapped). A cut that cannot move or has no beat in reach adds a `cut k: not snapped to a beat` warning and stays. After a repair moves a cut the edit is re-snapped with the same per-slot caps, so a swapped-in or dropped slot still lands every cut on a beat. The rule-based fallback runs with the same `--beats` grid.
- **Budget.** Every call is charged to `WORKSPACE/llm_spend.json` and capped by `llm_budget_usd`. The ledger is cumulative across runs and phases, so the cap applies to its running total — for a per-round budget set `--budget-usd` to the ledger total plus what the round may still spend. A `BudgetExceeded` stops the loop, keeps whatever valid artifacts exist and falls back to the rules (or exits 3 with `--no-fallback-rules`).
- **Fallback.** `scripts/director.py` is run as a subprocess with the same workspace, brief and parsed hints; its edit is copied to `--out` and the summary reports `status: "fallback"`, `fallback: "rules"`. The director code is never imported.

## Notes

- Re-run safety: when `--out` exists, validates and is newer than the shotlog, the brief file and `shot_plan.json`, nothing is written and the summary reports `status: "skipped"`. `--dry-run` always runs the screenwriter.
- The rule-based `scripts/director.py` stays the deterministic tool; this one is the model-driven loop on top of the same shotlog and the same editing rules.
- Outputs go to the workspace, never into the footage folder. For the deterministic cut see the `director` skill; for the render see `render`.
