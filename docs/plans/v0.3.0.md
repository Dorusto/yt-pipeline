# v0.3.0 plan — the director as a plugin for any coding agent

## Goal

v0.3.0 makes the director usable as an extension of any coding agent — a Claude
Code plugin, opencode, or any tool that reads the Agent Skills format — through
one `yt` entry point, and gives it a chat with the user that is honest about its
tools, a standard starting playbook with a per-instance style, a size-limited
learning notebook, and a sponsor sentence as fixed channel text. The web app
keeps the OpenRouter path; the plugin lets the host agent do the thinking on the
user's own subscription.

### Lot 2 — `yt` entry point on PATH

**Issue:** #82.

**Files:** `scripts/yt.py` (new), `bin/yt` (new, executable),
`docs/AGENT_SETUP.md`, `docs/guides/tools.md`, `tests/test_yt_entry.py` (new).

**What the user sees:** `yt transcribe ...`, `yt recap ...`, `yt doctor` work from
any folder, not only from the repository root.

**Design:** `yt <tool> [args]` resolves the repository root (`YT_PIPELINE_HOME`
first, else walk up from the script to the folder holding `scripts/` and
`requirements.txt`), the Python (`YT_PIPELINE_VENV`, else
`<root>/.venv/bin/python`, else `python3`), and runs `scripts/<tool>.py` with the
remaining arguments. `yt --help` lists the tools; an unknown tool is a usage
error (exit 2).

**Acceptance:** `yt --help` exits 0 and lists the tools; `yt doctor --help` exits
0; an unknown tool exits 2 with a message naming the tool; a test resolves the
root and dispatches to a stub tool.

**Out of scope:** creating the virtual environment (that is lot 3).

### Lot 3 — Claude Code plugin packaging and marketplace

**Issue:** #82.

**Files:** `.claude-plugin/plugin.json` (new),
`.claude-plugin/marketplace.json` (new), `bin/yt` (from lot 2),
`hooks/hooks.json` (new), `docs/AGENT_SETUP.md`,
`tests/test_plugin_manifest.py` (new).

**What the user sees:** `claude plugin marketplace add Dorusto/yt-pipeline` then
`claude plugin install yt-pipeline@yt-pipeline`; the skills appear as
`/yt-pipeline:yt-recap`, `/yt-pipeline:yt-director` and so on, from any folder.

**Design (from the official docs, cited in References):**

- The repository root is both the plugin root and the marketplace root.
- `.claude-plugin/plugin.json`: `name` `yt-pipeline` (only `name` is required),
  plus `version`, `description`, `author`, `license` `AGPL-3.0-or-later`,
  `skills: ["./.claude/skills/"]` (the `skills` key adds to the default `skills/`
  scan; every path is relative to the plugin root and starts with `./`).
- `.claude-plugin/marketplace.json`: `name` `yt-pipeline`, `owner`, and one
  `plugins` entry `{ "name": "yt-pipeline", "source": "./" }` (a relative source
  is written from the marketplace root; `"./"` is the marketplace root).
- `bin/yt` is the entry point the plugin puts on the Bash tool's `PATH` while it
  is enabled; it resolves the plugin root from its own location and uses a
  virtual environment under `${CLAUDE_PLUGIN_DATA}` (the plugin data directory,
  `~/.claude/plugins/data/yt-pipeline/`), falling back to `YT_PIPELINE_HOME` and
  `<root>/.venv` for a local checkout.
- `hooks/hooks.json` carries a `SessionStart` hook (top-level `hooks` key) that
  creates that virtual environment from `requirements.txt` on first run and after
  an update, idempotently.

**Format facts (from the official docs, not guessed):**

- A plugin is a directory with an optional `.claude-plugin/plugin.json` manifest;
  only `name` is required. Skills live in `skills/<name>/SKILL.md`; the `skills`
  manifest key adds directories to the default `skills/` scan. Every component
  path is relative to the plugin root and starts with `./`. `bin/` is on the Bash
  tool's `PATH` while the plugin is enabled. Hooks live in `hooks/hooks.json`
  under a top-level `hooks` key. `${CLAUDE_PLUGIN_ROOT}` is the install directory
  and `${CLAUDE_PLUGIN_DATA}` is a directory that survives updates.
- A marketplace is a directory with `.claude-plugin/marketplace.json`; it needs
  `name`, `owner` and a `plugins` array; each entry needs `name` and `source`; a
  relative `source` is written from the marketplace root, and `"./"` is the
  marketplace root. The install id is `<entry-name>@<marketplace-name>`.

**Acceptance:** a Python test checks the JSON shape against the documented fields
(manifest `name`; marketplace `name`, `owner`, `plugins[].name`/`source`; the
`skills` path exists); `claude plugin validate .` is a manual step for Doru (the
build host has no `claude` CLI).

**Out of scope:** submitting to Anthropic's directory; the MCP server.

**Hard:** yes — plugin packaging runs with the coder-max agent.

### Lot 4 — Agent guide for any agent + skills-in-guide check

**Issue:** #82.

**Files:** `docs/AGENT_SETUP.md`, `tests/test_agent_setup.py` (new), `README.md`
(only if a link is needed).

**What the user sees:** one guide that installs the pipeline for Claude Code,
opencode and any Agent Skills tool, names the `yt` entry point and the plugin,
and ends with a smoke test.

**Design:** rewrite `docs/AGENT_SETUP.md` as the guide for any agent (install, the
`yt` entry point, the Claude Code plugin, opencode, other Agent Skills tools,
smoke test). A test checks that the skills listed in the guide match
`.claude/skills/` (the guide today still lists 3 skills; there are 34). opencode

`~/.claude/skills/`, walking up from the working directory to the git worktree;
each `SKILL.md` needs `name` and `description` frontmatter, `name` must be 1–64
characters, lowercase alphanumeric with single hyphens, and match the directory
name, and `description` is 1–1024 characters.

**Acceptance:** the new test passes and fails when a skill is added to
`.claude/skills/` and not to the guide.

**Out of scope:** the fresh-container test (lot 11).

### Lot 5 — Starting playbook

**Issue:** #106 point 1.

**Files:** `prompts/playbook.md` (new), `prompts/screenwriter.md`,
`prompts/editor.md`, `prompts/reviewer.md`, `docs/guides/tools.md`,
`tests/test_prompts.py` (new or existing).

**What the user sees:** the director starts from the same structure on every
instance — the editing techniques it knows and the tools it can call, both the
ones that find problems (shaky clips, missed beats, loudness, gaps in the edit)

**Design:** one `prompts/playbook.md` holding the standard structure and the tool

**Out of scope:** the per-instance style (lot 9).

### Lot 6 — Director agent mode: prepare and apply, no OpenRouter key

**Issue:** #82 (the owner's "two modes, one set of tools" direction).

**Files:** `scripts/llm_director.py`, `prompts/`, `docs/guides/tools.md`,
`.claude/skills/yt-llm-director/SKILL.md`, `tests/test_llm_director_agent.py`
(new).

**What the user sees:** from the plugin, the director runs on the host agent's own
subscription, with no OpenRouter key.

**Design:** `llm_director.py --prepare --workspace W` writes the inputs the agent
needs (the brief, the eligible shotlog rows, the rules, the required output paths
and schemas) to `<workspace>/director/inputs.md` and exits without a model call;
the host agent writes `shot_plan.json` and `edit.json`;
`llm_director.py --apply --workspace W` validates them against the schemas and
the editing grammar, repairs mechanical faults with the existing machinery, and
writes the final `edit.json` with `meta.director.agent = true`. The OpenRouter
path stays the default for the web app.

**Acceptance:** a test with a synthetic workspace: `--prepare` writes the inputs
and makes no model call (mock backend); a hand-written valid plan and edit pass
`--apply`; an invalid edit is repaired or rejected with a clear error naming the
rule.

**Out of scope:** the same split for the writing tools (metadata, `recap_meta`,
chapters, Shorts ranking) — later.

**Hard:** yes — the prepare/apply split runs with the coder-max agent.

### Lot 7 — Director chat: the reviewer's objections in plain words

**Issue:** #96 points 1 and 2.

**Files:** `scripts/serve.py` (a stable file — the commit carries
`Stable-change: approved`), `scripts/llm_director.py`,
`prompts/interpret_feedback.md`, `scripts/common/theme.py`,
`docs/guides/user-guide.md`, `.claude/skills/yt-recap/SKILL.md`,
`tests/test_serve_chat.py` (new).

**What the user sees:** a chat with the director on the project page. The user
says what they like and what they do not; the director answers first how it reads
the request, with a cost and time estimate; the user approves and only then the
new version is made. The reviewer's objections appear in the same chat in plain
words, next to the shot they name by its number on the timeline.

**Design:** replace the "Ask the director" reply page with a chat panel; the
reviewer verdict (`edit.json meta.director.review`) is rendered as plain
sentences; the approve button starts the run. One cheap model call for the
answer; no run without approval.

**Acceptance:** tests for the chat route (a message in, a reply out), the
plain-words rendering of the reviewer notes, and the approve flow; the reviewer
box stays gone.

**Out of scope:** the learning notebook (lot 10).

**Hard:** yes — the chat loop runs with the coder-max agent.

### Lot 8 — Director honest about its tools + missing-tool log

**Issue:** #96 point 3 (the honest answer and the log).

**Files:** `scripts/llm_director.py`, `prompts/interpret_feedback.md`,
`scripts/serve.py`, `scripts/common/` (the requests store),
`docs/guides/user-guide.md`, `tests/`.

**What the user sees:** when the director cannot do what the user asked, it says
so in plain words — what it can do and what it cannot — and the request is
recorded so the owner sees which tools the director needs next.

**Design:** the interpret-feedback prompt gets the fixed capability list from the
playbook (lot 5); the answer is structured (`reply`, `can_do`, `missing_tool`);
when `can_do` is false the director says what it can and cannot do, and
`serve.py` appends a `missing_tool` line to the requests file.

**Acceptance:** a test that a request for an unsupported action yields
`can_do: false`, a plain-word answer and one log line.

**Out of scope:** building the missing tools.

### Lot 9 — Per-instance style settings

**Issue:** #106 point 2.

**Files:** `scripts/common/channel.py`, `scripts/metadata.py`,
`scripts/recap_meta.py`, `config.yaml.example`, `docs/RULES.md`,
`docs/guides/tools.md`, `tests/`.

**What the user sees:** the channel wording, title style, description order, the
voice of the pinned comment and the thumbnail formula come from the instance's
own settings, not from code.

**Design:** extend the instance config with the style parts (title style,
description order, pinned comment voice, thumbnail formula); `channel.fixed`
already holds the fixed wording. The code reads them; a missing part falls back
to a neutral default, never to built-in channel text.

**Acceptance:** tests that the style values come from the config and a missing one
falls back to a neutral default.

**Out of scope:** the notebook (lot 10).

### Lot 10 — Learning notebook with a size limit

**Issue:** #106 point 3 and 4; #96 point 3.

**Files:** `scripts/notebook.py` (new), `schemas/notebook.schema.json` (new),
`scripts/llm_director.py`, `scripts/serve.py`, `prompts/`, `docs/`,
`.claude/skills/yt-notebook/SKILL.md` (new), `tests/test_notebook.py` (new).

**What the user sees:** the director learns from the feedback on each edit and
writes short lessons into the instance's own notebook; it reads the notebook
before every new edit; the user can see the notebook in the app and delete a
wrong lesson.

**Design:** a per-instance notebook file with a fixed size limit. After each edit
an agent pass writes short lessons; before each edit the director reads it; a
write that would pass the limit fails and the agent must first merge overlapping
entries or remove stale ones, then retry. Each cleanup shows what changed.

**Acceptance:** tests for the size limit (a write past the limit fails with a
clear error), the merge/remove path, the director reading the notebook, and the
app showing and deleting a lesson.

**Out of scope:** the shared notebook between instances (see Out of v0.3.0).

**Hard:** yes — the notebook limit runs with the coder-max agent.

## Questions for the owner

1. **Sponsor sentence — wording and place** (#114). Options: (a) its own
   paragraph right after the intro, before the links; (b) at the end, after the
   closing line; (c) after the subscribe line. Recommended: (a). The wording
   itself is the owner's; the plan uses a neutral placeholder.
2. **Where the chat lives** (#96). Options: (a) a new "Director" tab; (b) inside
   the Recap tab, under the player; (c) a floating panel on every tab.
   Recommended: (b).
3. **Where the notebook is shown** (#106). Options: (a) a "Notebook" section on
   the Costs page; (b) a new tab; (c) a collapsible section on the project page.
   Recommended: (a).
4. **Where the missing-tool log goes** (#96). Options: (a) the existing requests
   file, with `type: missing_tool`; (b) a separate `missing_tools.jsonl`;
   (c) shown in the app only. Recommended: (a).
5. **Plugin and marketplace name** (#82). Options: (a) `yt-pipeline`; (b)
   `yt-director`; (c) `yt`. Recommended: (a).
6. **What the director says when it cannot do something** (#96). Options: (a) a
   short neutral sentence plus "I have noted it"; (b) a longer sentence naming
   what it can do instead; (c) a neutral placeholder until the owner writes it.
   Recommended: (a), with the exact wording left to the owner.
7. **Notebook size limit** (#106). Options: (a) a fixed number of lessons (for
   example 40); (b) a fixed character count (for example 4000); (c) a fixed file
   size (for example 8 KB). Recommended: (a).
